It invokes `npm run validate:form-designer` sequentially, prevents overlapping runner executions, and retains the command log and source/browser fingerprint. A cached PASS is reusable only while its fingerprint and log hash match; failures and source changes during execution never produce PASS. `-Force` reruns it; `-FingerprintOnly` only reports identity and is not test evidence. Do not edit frontend source, fixtures or browser scripts during a browser run: Vite can reload the page and invalidate the result. Form-specific API, SQL, approved-release and browser acceptance remain separate requirements; a shared cached PASS never activates a form or replaces owner approval.

- Preserve owner-approved behavior and existing drafts; do not silently reset, discard history, or change the master when editing an independent form.
- Shared toolbar behavior is versioned in `laboratoryToolbarContract`, documented in `docs/form-laboratory-toolbar-contract.md`, and included in the integration behavior manifest. Reusable fixes belong in this shared renderer; verify short-header content containment, live upward resizing, unchanged typography, saved child overrides and independent document storage before completion. Promoting a form's geometry to the master still requires explicit target selection.
- For changes touching Form Laboratory, shared presentation, Designer, structural editing, recovery or their CSS, run `npm run validate:form-designer` from `frontend` before reporting completion. It runs focused behavioral tests, session tests, TypeScript and real headless-browser tests.
- Keep the development site at `http://127.1.0.1:5173/`. Browser tests use a disposable profile and synthetic data. Chrome/Edge must be available; browser startup failures are validation failures, never a silent skip. Set FORM_TEST_BROWSER only to an installed browser executable if necessary.
- If a regression fails, fix the implementation and rerun relevant checks. Do not weaken an approved contract or mark visual success based only on source-text tests. Add a regression for each corrected defect.
- Persian user-facing text and reports must be right-to-left.
- Toolbar regression tests must operate on the actual button/input, not just its wrapper. Cover independent search input/reverse button/each option selection, Ctrl/Command multi-selection with a visible union frame and atomic drag/one-step Undo, pinned side controls with a flexible center, selected-only handles, numeric and mouse header sizing, multiple header hosts and persistence. Check horizontal overflow separately even with fixed editor height and old offset Canvas data.
- Header fields and table toolbar parts use the existing Designer and font dialog. Selecting an element reveals only its corresponding sidebar controls; do not scroll or resize the canvas to reveal settings.
- Dropdowns and submenus must overlay the form without reflow or covering their own trigger. Test them near the viewport bottom as well as the top.
- Remove unused scroll extents in the view layer without rewriting saved Canvas coordinates or restricting editing bounds. Keep explicit manual scrolling settings and the original Laboratory layout contract.
- Every Designer target (native field, composite/custom component, toolbar child/group and header panel) must support the same body selection/drag, multiselection, physical arrow movement, eight resize handles, shared font dialog and live appearance controls. Test actual nested controls, including Title-derived components; wrapper-only assertions are insufficient.
- During a gesture and Undo/Redo, keep the viewport origin, unselected rectangles and scroll position stable. Resizing an edge must leave its opposite edge fixed in RTL and LTR. Adding a header must not reflow or shrink existing panels; overlap is allowed until explicitly arranged.
- Growing a Designer canvas to fit its viewport changes bounds only; it must never translate stored field rectangles. Dragging one field moves only that field and its own label/parts, with all unselected rectangles, viewport origin and scroll offsets unchanged. Include a real RTL browser drag regression where the canvas starts narrower than its editor and the selected textarea is near the inline end, so responsive expansion cannot shift neighboring fields.
- Input rectangles define Designer drag bounds. Labels may span a whole row, while selection controls and error overlays may carry stale extents; translate all of them with the field, but never let their invisible bounds pin its drag. Keep the Move input hit target separate from all resize-edge/corner hit targets, and browser-test an unpinned RTL textarea near the inline end for both a leftward move and left-edge growth while checking every unselected rectangle and the viewport remain fixed.
- A manual field drag is an explicit placement and must commit without running `autoAlignDesignerCanvas`; otherwise the selected field can snap back to its previous row/column and appear immovable. Keep Ctrl+L as the explicit whole-layout command, and guard this behavior with a real pointer-drag browser regression.
- Resizing an input keeps a width-matched label attached to the resized edge and width; selection chrome and error overlays follow the input, while every unselected field stays fixed. If the row had persistent centering, preserve its center by adjusting selected geometry only. Ctrl+L persists that centering contract, centers the densest complete row, and aligns a one- or two-field incomplete row—including a newly added field—to that row's reading edge (right in RTL, left in LTR), not to the outer canvas boundary; do not re-center it in a second layout pass. Newly added labels inherit the shared label font settings unless the user sets an explicit per-field override. Cover each rule with regressions.
- Designer right-click must preserve an already selected group across fields, footer actions and table columns; Ctrl/Command-right-click adds an unselected target without toggling a selected target out. Delete and context-menu removal operate on the full applicable selection in one structural-history step. Required footer actions are never removed, operational table rows are never inferred from Designer selection, and Undo restores every removed member. Keep real browser regressions for all three structural target types and keyboard deletion.
- Ctrl+L must lay out within the existing Canvas width, capped at the editor's available width when an old Canvas is oversized. It may grow only to the minimum normalized content width plus equal half-centimeter edge insets; never expand the Canvas to the viewport merely because Ctrl+L was pressed. Cover both fit-without-growth and minimum-growth cases.
- A fixed-geometry upper editor must consume horizontal whitespace as its viewport narrows, centering the unchanged field-and-label group while it fits and keeping half-centimeter margins before its own horizontal scroll begins. Responsive fitting is a render-only projection: never rewrite saved Canvas rectangles, and never let the lower table's independent width or scroll range enlarge the upper editor.
- Fixed-geometry viewport sizing reserves a stable scrollbar gutter and measures the editor's padding-free content width, so scrollbar visibility cannot feed back into the fit threshold. The layout inspector must compensate for the explicit view-only Canvas translation while still reporting actual part-size or position changes; cover both threshold crossings and true-geometry warnings.
- Keep upper-editor scrolling latched with hysteresis: enter at a 5 mm edge inset and release only at 8 mm while growing. Preserve real overflow during the latched interval and verify shrink/grow transitions without changing saved field geometry or lower-table width.
- Footer actions support Ctrl/Command multi-selection for group resize, dimensions, font and color, and optional-action deletion; text/code editing stays single-action only. Never let group operations alter labels or shortcuts, and never delete required actions. Cover group resize and schema removal with regression checks.
- Component test mode uses local temporary sample state, never operational requests or design history entries. Returning to Design must preserve schema, styling, geometry and component definitions.
- Title, address and renamed list instances must use the same FormValueList/NumberControl interaction engine. PersonTitleControl is only a data adapter. Labels must drive help, placeholders and action names, never choose behavior. Keep stable library IDs and immutable revisions; inherited capabilities update dependent instances while explicit child overrides and data/API bindings remain intact.
- Every list popup must render in the shared opaque overlay, outside field opacity/transform/stacking contexts. Test empty gaps and underlying toolbar text, Enter batch rows, F3 versus parent save, edit/delete/default and Escape in the real Persons page as well as synthetic forms. Removing a row must not be mistaken for an outside click after its DOM node is removed.
- Component sample mode must not disable toolbar selection/context menus/dragging. Include this exact mode in the browser regression matrix.
- Form behavior originates in the Laboratory behavior library. Documents and components keep stable references and explicit differences, not copies of the shared engine. Keep reusable source/operation instructions, immutable revisions and preview-before-publish; include the resolved behavior manifest in integration releases.
- Test the full local runtime cycle: Create, only Save/Close during entry, validation, component Enter versus field navigation, saved sample rows, edit/cancel, normal actions after save and a stable return to Design. Reset temporary data when switching forms; never invoke operational APIs from this runtime.
- Runtime preview must render the existing designed actions through the same footer/Shortcut renderer. Preserve action IDs, labels, shortcut text, colors, fonts, border, radius and size; switch only visibility, availability and local behavior. Compare computed custom appearance before runtime, in Create/Edit and after Save in browser regression tests; do not introduce a separate plain-button runtime footer.
- Context menus for individual toolbar parts must expose their own typography/colors/box controls. Structural header commands belong to header targets. Switching between preview and design datasets must use current value adapters on the first render while preserving grid geometry and user column settings.

## Operational form redesign and shared theme contract

- New activations must pass `operationalAcceptanceBlockers` in `frontend/src/components/base-form/operationalAcceptance.ts`. Saving/approving a design, using the shared grid, or passing schema tests is not operational acceptance. Every schema table requires release/digest-bound test evidence for server paging/search/filter/sort/filter options, stable page ordering, bounded rendering, large datasets, row binding and sticky-header controls; cascading hierarchies additionally require lazy branches, ancestry search and copying without loading the full tree.
- Run `npm run test:operational-contract` from `frontend` for release-gate changes. Run the new form's actual API/browser/load tests separately and retain their artifacts; the shared fixture is not evidence that a different form's backend is integrated. Missing, failed or blocked evidence must prevent a new integration receipt. Do not add grandfathering exceptions; the sole pre-gate Product Group activation is retained only to preserve its existing route and does not certify large-data readiness.
- `createFormDesignExport` embeds per-table acceptance requirements. Preserve approved design JSON, user overrides and data while completing missing adapters. Never substitute browser filtering/full-tree loading for the required SQL queries/lazy hierarchy and call the form ready for high volume.

- Every new or replacement operational form must use `OperationalFormFrame`: fixed outer height independent of row count, search results and CRUD mode; internal table scrolling; equal horizontal table insets; footer stays at the bottom.
- Put personal form settings in the top bar. Enforce the document's customization permissions when reading, displaying and saving per-user overrides. Do not expose structural Designer controls or modify the pinned design/master from this panel.
- Permitted personal customization must reuse Laboratory's `DesignerFontPanel`, `ExcelColorPicker` and pointer/resize helpers. Enter customization from the top bar, select the permitted field/label with the mouse and resize the frame with handles; do not introduce a separate numeric-only customization dialog. Operational captions omit design-stage suffixes. Saved toolbar widths must remain contained in the current viewport; column resizing must change only the selected column.
- The shared operational behavior contract lives in `frontend/src/components/base-form/laboratoryOperationalBehavior.json`; every generated form-design JSON must embed its complete snapshot so the same design carries its behavior. The runtime reads its formatting target allowlist and selectors from that contract. Color and typography permissions cover the form title/header, editor and notice panels, every table-toolbar part (including search/options), table background, headers, rows and data columns; the title may be styled but never repositioned. Reuse the Laboratory context-menu groups, `DesignerFontPanel` and `ExcelColorPicker`, without changing Laboratory behavior. Keep field focus visible after blur until save/exit, and move the indicator when another field receives focus. Tables start at logical inline-start (right in Persian, left in English), only scroll when content exceeds the usable viewport, and resize one column by dragging its logical end. Persist allowed column widths plus table-header and toolbar-header heights per user and form; settings mode must support Save or Exit without saving, while permitted normal-mode resizing saves immediately. Collapse an empty notice so no gap appears between the banner and editor. Give each grid an independent search-radio group and keep the checked option bold. Personal settings replace the gear with explicit Save and Exit without saving actions.
- Contract version 2 also requires the icon-only XLSX action beside expand/columns, with a tooltip and formatted export through `exportGridWorkbook`; every column filter must provide reversible invert-selection beside Select All, and the search toolbar must retain its separate reverse-results toggle. Keep `docs/form-design-access.md` aligned with this contract. New forms inherit these shared behaviors and must not implement form-specific copies.
- Verify empty search, one row, many rows, Create/Save and personal-settings persistence with the focused operational-form browser fixture before reusing or replacing a form.

- Keep the working operational original available. Redesigns are independent, versioned documents in the existing Laboratory Designer, with stable IDs and separate schema, appearance and history.
- Classify changes to bindings, types, validation, actions, table relationships or business behavior as requiring integration review. A browser design release must never activate or replace an operational route by itself.
- Before replacing a working form, verify its actual source/API/database contracts, migrations if needed, permissions, sorting and Master-Detail behavior; require tests, owner approval and a rollback path.
- Master revisions require an explicit target selection. Preserve form-specific and per-user overrides; show conflicting decisions instead of silently overwriting them.
- Author shared themes in the Laboratory. Ordinary users receive only permitted own-account preferences; theme editing must not grant structural or operational access.
- Catalog placeholders and partial routes must be labeled honestly; a synthetic redesign seed is not a completed migration of a live form.
