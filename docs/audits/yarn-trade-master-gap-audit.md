# ممیزی انطباق Yarn Trade با Master

**تاریخ ممیزی:** 2026-11-15
**شاخه و مبنا:** `review/br-01b-form-template`، commit `009e0f28e71d835e97d8ab94e0c3e6e87d3fee0f`
**مرجع مورد تأیید مالک:** [`YARN_TRADE_CODEX_MASTER.md`](../../YARN_TRADE_CODEX_MASTER.md)

## خلاصه اجرایی

سامانه یک monolith ماژولار React/TypeScript و ASP.NET Core/EF Core با SQL Server است. در هستهٔ خرید، فاکتور و هزینه‌ها، سفارش خرید، انبار، لایه‌های بهای تمام‌شده، ثبت فروش، ثبت دریافت/پرداخت و دفتر شرکا وجود دارد. ارزش حفظی کار قبلی شامل مدل عملیاتی خرید/فروش موجود، تراکنش و retry در posting، RowVersion، قفل‌گذاری موجودی برای فروش هم‌زمان، دفتر حرکات و قواعد قرارداد تاریخ‌دار است؛ بازنویسی کلی شواهدی ندارد.

با این حال، سامانه هنوز گردش هدف Master را کامل نمی‌کند. خرید، رسید واقعی انبار، محموله، محاسبهٔ نهایی بهای تمام‌شده و lifecycle طلب شریک، همگی یک مدل پیوسته و تاریخ‌پذیر ندارند. برای ورود تاریخچه، دو ناسازگاری بحرانی‌اند: هنگام ثبت خرید، تاریخ رسید لایه/حرکت «اکنون» است نه تاریخ واقعی تاریخی؛ و مقدار فاکتور مستقیماً موجودی دریافتی می‌شود. ورود فاکتور مستقل از PO ممکن است، اما workflow کامل catch-up وجود ندارد. توصیه: تا تعیین راهکار تاریخ/رسید/مقدار و reconciliation، دادهٔ واقعی دو ساله به این posting متصل نشود.

این ممیزی روی سورس، مستندات و migrationهای موجود استوار است؛ پایگاه SQL در حال اجرا یا UI زنده در این نوبت خوانده نشده است.

## یافته‌های معماری و پایگاه داده

1. **حفظ posting اتمیک و tokenها:** `PostingService.PostPurchaseAsync`, فروش و endpointهای مالی از transaction، execution strategy و concurrency token استفاده می‌کنند. Master نیز این رفتار را حفظ می‌کند؛ این مرزها را در توسعهٔ افزایشی حفظ کنید.
2. **تاریخ کسب‌وکار و زمان فنی از هم جدا نشده‌اند:** فاکتور `InvoiceDate` دارد، ولی لایه و حرکت خرید هر دو زمان جاری می‌گیرند. FIFO فروش براساس `ReceivedAtUtc` مرتب می‌کند. ثبت دیرهنگام دادهٔ قدیمی، ترتیب واقعی FIFO را بازسازی نمی‌کند.
3. **مدل تدارک هنوز shipment-first نیست:** مدل فعلی invoice-centric است. Migration `20260727120000_AddPurchaseOrders` PO را افزوده و به invoice ارجاع nullable داده؛ این با پل مهاجرتی DB-02 Master سازگار است، اما در commit فعلی Shipment/OriginLot/receipt domain دیده نشد.
4. **قرارداد کسب‌وکار با تاریخ سند:** `BusinessContractService.ResolveForDateAsync` در posting خرید، فروش و سند وجه به کار می‌رود و نسخه روی سند نگه‌داری می‌شود. پوشش تاریخچه مستلزم واردکردن نسخه‌های مؤثر و حل gap/هم‌پوشانی پیش از posting است.
5. **برند/شخص:** migration و mapping یک قید یکتای BrandId در جدول واسط دارند (نام migration `UniqueBrandOwner`). این با رابطهٔ چندبه‌چند Master تعارض بالقوه دارد؛ پیش از تغییر باید رکوردهای واقعی و هدف تجاری تأیید شود.
6. **تاریخچهٔ migration:** migrationها در `src/YarnTrade.Api/Data/Migrations`; آخرین تغییرهای شناخته‌شده برای فرم نخ و ساختار انبار در این snapshot هستند. تنها مدل EF و migration بررسی شده؛ این بررسی معادل `database update`, مقایسهٔ schema زنده یا تأیید rollback نیست.

## نقشهٔ کار کم‌هزینه و ترتیبی

1. **حفاظت و baseline:** snapshot پشتیبان قابل بازیابی و ثبت نسخهٔ DB/تعدادها/جمع‌های کنترلی در محیط آزمایشی؛ A8 و محدودیت‌های واقعی اجرا بررسی شوند.
2. **قفل تصمیم‌های مالک:** واحد/مقدار مورد اعتماد، تعریف تاریخ receipt، قاعدهٔ مقدار کسری، مبنای تخصیص هزینه، نسخهٔ قرارداد تاریخی، تفکیک سرمایه/طلب، پرداخت و FX. برای Phase F سناریوهای عددی الزامی است.
3. **پایلوت تاریخچهٔ غیرواقعی/کپی‌شده:** یک خرید با تاریخ قدیمی، هزینه با تاریخ متفاوت، receipt کسری، فروش بعدی، دریافت/چک، reversal و تطبیق مانده؛ صرفاً پس از طراحی تاریخ و receipt. خروجی را با کاغذ/Excel مرجع تطبیق دهید.
4. **افزودن حداقلی receipt و catch-up:** پیش از توسعهٔ گردش PO آینده، رسید واقعی با تاریخ و مقدار مستقل، audit و نگاشت invoice→receipt→layer را طراحی کنید. ورودهای مستقل از سفارش را مسیر اول قرار دهید؛ PO/shipment آینده را Phase B مجزا نگه دارید.
5. **هزینهٔ نهایی و دفتر:** lifecycle هزینهٔ موقت/قطعی/اصلاح، اثر آن بر layer و فروش‌های قبلی، سپس مدل claim/capital را با تصمیم‌های عددی پیاده کنید. بدون اصلاح بی‌ردپا؛ اصلاح باید ledger/reversal قابل ردیابی باشد.
6. **گزارش reconciliation و cutover:** ماندهٔ افتتاحیه، موجودی، FIFO، فروش/دریافت و شریک را دقیق تطبیق دهید؛ سپس محدودیت‌های استفاده و rollback را مستند کنید.

## تصمیم‌های مالک واقعاً لازم

- برای خرید تاریخی، تاریخ واقعی ورود موجودی چیست و چه evidentiary source آن را ثابت می‌کند؟ آیا چند رسید برای یک فاکتور ممکن است؟
- در اختلاف فاکتور و رسید، کدام مقدار موجودی/هزینه/بدهی را تعیین می‌کند و تلورانس/کسری چگونه ثبت می‌شود؟
- هزینهٔ دیررس چگونه به lotها و فروش‌های قبلی تخصیص/اصلاح می‌شود و آیا دورهٔ قطعی‌شده reopen می‌شود؟
- سرمایهٔ شریک، طلب قابل پرداخت، سود، credit premium و وجه وصول‌نشده در سناریوهای نقد/اعتباری چگونه محاسبه می‌شوند؟ Master بخش 12 را مرجع تصمیم‌های معوق قرار داده است.
- FX خرید ارز و حواله، ماندهٔ دوارزی و اضافه/کسری تسویه چگونه است؟
- مالکیت Brand واقعاً چندبه‌چند است یا قید فعلی یک مالک، قاعدهٔ تجاری مورد نظر است؟
- برای چک خارج از سامانه، امضای تحویل و مسئولیت چک برگشتی/فروشگاه چه تصمیمی دارد؟

## محدودیت‌های راستی‌آزمایی

- سورس، docs و EF migrations بررسی شد؛ در این نوبت SQL زنده متصل نشد، هیچ migration روی DB اجرا نشد و data integrity واقعی/تعدادهای رکورد تأیید نشد.
- اپ را در مرورگر باز یا سناریوهای زنده اجرا نکردم؛ build/test اجرا نشد. نتایج تستی که Master یا docs نقل می‌کنند، سابقهٔ مستند پروژه‌اند نه اجرای مجدد این ممیزی.
- تنظیمات production، سطح دسترسی کاربران، اسرار محیط، backup/restore واقعی و حجم/کیفیت داده قابل مشاهده نبود.
- جدول مصفوفه، وضعیت را در سطح سورس قابل مشاهده بیان می‌کند؛ برای «کاملاً پیاده» بودن، لازم است UI+API+SQL در محیط نمایندهٔ واقعی اثبات شود.
