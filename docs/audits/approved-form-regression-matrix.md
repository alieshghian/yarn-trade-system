## اندازه‌گیری قابل تکرار

از پوشهٔ frontend دستور `node --test tests/approved-grid-stress.test.mjs src/components/base-form/excelGrid.test.mjs` را اجرا کنید. آزمون برای هر اندازه شناسه و ترتیب همهٔ خروجی‌ها را با نتیجهٔ مستقل مقایسه می‌کند. جدول زیر یک جفت اجرای محلی Node 24.19 را نشان می‌دهد. ستون‌های مرورگر از اجرای جداگانهٔ warehouses.browser.mjs، سرور توسعه و پاسخ‌های صفحه‌بندی‌شدهٔ آزمایشی هستند. این اعداد زمان SQL یا تعهد کارایی نیستند.

## گیت تحویل

برای هر قابلیت جدید، تصمیم مرجع، رفتار و موارد رد، آزمون مثبت و منفی، تعامل مرورگر، نتیجهٔ اجرای محدود و یکپارچه و یادداشت تغییر را هم‌زمان ثبت کنید. مالک قابلیت نتیجهٔ شکست را تا رفع یا تصمیم صریح باز نگه می‌دارد. فایل گردش کار .github/workflows/form-design-regressions.yml آزمون‌های آزمایشگاه، مرورگر هر فرم، ساخت تولیدی و بارگذاری تب‌ها، دادهٔ حجیم و یکپارچه‌سازی SQL را اجرا می‌کند. آزمون‌هایی که برای مهاجرت بانک توسعهٔ شخصی نوشته شده‌اند جزو این مسیر خودکار نیستند. اجرای SQL فقط روی نمونهٔ موقت انجام می‌شود.

مدیر مخزن پس از نخستین اجرای میزبانی‌شده باید وضعیت‌های presentation، theme-security، production-navigation، integration و هر پنج عضو Approved form workflows را برای شاخهٔ master الزامی کند. پیکربندی شاخه از روی فایل محلی قابل تأیید نیست. آزمون شکست‌خورده یا اجرای فاقد مرورگر مجوز پذیرش نیست. فایل 00_INDEX.md در درخت همین مخزن پیدا نشد؛ بستهٔ خارجی احتمالی به‌عنوان منبع بررسی‌شده ثبت نشده است.

## پیگیری شکست‌های اجرای ۱۹ نوامبر ۲۰۲۶

### آزمایشگاه و بازیابی

قرارداد تعامل با ماوس این است که انتخاب و گرهٔ ورودی ثابت بمانند، پیش‌نمایش فقط جعبهٔ انتخاب‌شده را روی صفحه تغییر دهد، ثبت هندسه هنگام رهاکردن انجام شود و یک Undo کل حرکت را برگرداند. در آزمون توسعه، Profiler ریشه دو commit را دید. تایمر ۱۸۰ میلی‌ثانیه‌ای بازیابی بعد از آغاز تراکنش و پیش از اولین نقاشی اجرا می‌شد، چون کنترل‌های ثبت‌شده نشانگر حرکت را تازه در اولین نقاشی می‌گذاشتند. نوشتن نسخهٔ بازیابی باعث افزایش recoveryRevision در FormLaboratoryPage و رندر فرزندان طراح شد. اثر همگام‌سازی ستون‌ها در BaseFormGridBoundary یک commit دیگر داشت. PendingFormDesignMenu هم در ردگیری دیده شد. شرط صفر رندر برای حرکت حفظ شد؛ نشانگر قاب اکنون هنگام فشردن ماوس تنظیم و در مسیر پایان یا لغو پاک می‌شود. ایجاد نقاشی همچنان تا حرکت واقعی صبر می‌کند.

در مقایسهٔ جداگانه با React تولیدی، همان حرکت سریع پیش از اصلاح ۳۷ ← ۳۷ و نگه‌داشتن دکمه تا سررسید بازیابی ۳۶ ← ۳۸ بود؛ شمارهٔ بازیابی از ۴ به ۵ رسید. پس از اصلاح، تعامل با ماوس در هر دو حالت توسعه و تولید بدون commit حین حرکت، با همان ورودی نصب‌شده، اندازهٔ مورد انتظار و Undo صحیح گذشت. مقایسهٔ تولیدی با بستهٔ جداگانهٔ آزمون و دادهٔ مصنوعی انجام شد.

پوشش این نسخه ۳۹ از ۵۲ قابلیت ثبت‌شده (۷۵٪) است. مخرج شمار اقلام موجود در ثبت است و شمار همهٔ فیلدها و تعامل‌های بالقوهٔ محصول را نشان نمی‌دهد. ۱۳ مورد `unverified` شاهد کافی ندارند. از جمله تصویر کامل اصیل برای چند فرم، جزئیات XLSX و بزرگ‌نمایی سایر فرم‌ها، و ماتریس مرورگری اصلاحیه و نقش قرارداد. روی نسخهٔ شناخته‌شدهٔ معیوب تصویری به‌عنوان مرجع تأییدشده اضافه نشد. طرح‌های نسخه‌دار، مختصات یا ظاهر منتشرشدهٔ موجود را جدا از کد رابط نگه می‌دارند.

### مسیرهای اجرا

- توسعهٔ سریع: از `frontend`، `npm run test:approved -- unit` یا مسیر یک سناریو مانند `npm run test:approved -- person-brand-lookup`. حالت پیش‌فرض همهٔ سناریوهای فرانت‌اند، TypeScript و ساخت تولید را اجرا می‌کند.
- انتشار: `npm run test:approved -- all` به Node 24، مرورگر و runtime ‎.NET 8 با اتصال آزمایشی `YARN_TRADE_SQL_TEST_CONNECTION` نیاز دارد. سناریوهای UI در پروفایل تازه با API مصنوعی و سرویس loopback پرتابل اجرا می‌شوند. اجرای SQL باید با تنظیم سرور پایگاه آزمایشی انجام شود.
- آزمایشگاه: پذیرش مستقل را از ریشه با `scripts/Invoke-LaboratoryValidation.ps1` اجرا کنید. فایل‌های آزمایشگاه و نسخه‌های پیش‌نویس در ثبت عملیاتی فریز نمی‌شوند.
- اجرای روزمره: `runapp2.bat` بررسی سبک هش و حضور آزمون‌ها را قبل از Vite انجام می‌دهد. اعتبارسنجی انتشار و SQL در CI مستقل‌اند. زمان‌بندی هفتگی در همان workflow مشخص شده است.
- اثبات خطا: `npm run test:approved:faults` سه مسیر سالم را در کپی موقت اجرا می‌کند و هر خرابی را جدا اعمال می‌کند. نام آزمون آشکارکننده، کد خروج، خروجی و وضعیت در `frontend/test-results/fault-injection` ثبت می‌شوند. شکست عمومی ساخت یا راه‌اندازی به جای شکست آزمون موردنظر پذیرفته نمی‌شود.

### افزودن یا تغییر عمدی

۱. فرم‌های وابسته و منشأ تأیید را مشخص کنید. قابلیت مشترک در صورتی وارد فرم دیگر می‌شود که سازگاری و ارتقای همان فرم تأیید شده باشد.
۲. آزمون واقعی و شاهد پایدار آن را به مرحلهٔ موجود CI اضافه کنید. خروج موفق فرایند به‌تنهایی کافی نیست. گیت PASS نام‌دار مرورگر، گزارش TAP بدون skip/todo و نتیجهٔ TRX ثبت‌شده را بررسی می‌کند.
۳. مرجع، نسخهٔ محفوظ قبلی و تست‌های سازگاری را نگه دارید. ثبت نسخهٔ جدید را به انتهای فایل اضافه کنید. در PR و push، گیت فهرست قبلی را از Git مقایسه می‌کند. تغییر مرجع نسخهٔ قدیمی یا بازتولید خودکار عکس ممنوع است.
۴. برای تغییر مشترک تمام پنج سناریوی عملیاتی، تولید و یکپارچگی را اجرا کنید. سیاست موجود GitHub همان نه نام الزامی را کنترل می‌کند. گیت متمرکز در دل بررسی‌های الزامی اجرا می‌شود و `presentation` استقلال خود را حفظ می‌کند. بررسی الزامی `production-navigation` هر وضعیت پیش‌نیاز غیر از `success`، از جمله `skipped` و `cancelled`، را رد می‌کند.
