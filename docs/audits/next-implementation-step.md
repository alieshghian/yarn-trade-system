## اولین بسته: ثبت رسید واقعی و محافظت تاریخ موجودی

یک بستهٔ کوچک backend و schema افزایشی بسازید که به فاکتور مستقل از PO، یک یا چند رسید واقعی انبار با تاریخ و مقدار مستقل متصل کند و فروش را از مصرف رسید آینده منع کند. این بسته به‌تنهایی به معنی آمادگی کل خرید تا فروش و محاسبات نهایی شریک نیست.

**کد قابل استفاده و فایل‌های اصلی:** `src/YarnTrade.Api/Domain/Entities.cs`, `Data/AppDbContext.cs` و `Data/Migrations/` برای مدل؛ `Controllers/PurchasesController.cs` و `Services/PostingService.cs` برای قرارداد و posting؛ `Services/BusinessCalculations.cs` برای تخصیص؛ `tests/YarnTrade.Tests/InventoryConcurrencyTests.cs`, `SalePostingAuthorityTests.cs`, `RowVersionConcurrencyTests.cs` برای الگوهای آزمون. تراکنش، execution retry، RowVersion، audit، قفل‌های SQL فروش و lineage موجود `SaleCostAllocation` حفظ شوند.

**حداقل تغییر پیشنهادی:**

1. header و line رسید با شناسهٔ فاکتور/ردیف، انبار، تاریخ مؤثر، مقدار واقعی، وضعیت و RowVersion؛ FK و قیدهای لازم و کلید یکتای درخواست برای جلوگیری از ثبت مضاعف. invoice و مقدار آن تغییر نکند. تفاوت مقدار مشاهده و ثبت شود؛ تصمیم مالی آن خارج از این بسته است.
2. API محدود برای ایجاد/خواندن و قطعی‌کردن receipt؛ اعتبارسنجی server-side، مجوز، audit و تراکنش اتمیک؛ ساخت layer/movement فقط برای مقدار واقعی و با lineage به receipt line. timestamp ثبت فنی جدا از تاریخ مؤثر باشد.
3. تاریخ مؤثر قابل استناد و ارتباط receipt به layer افزوده شود؛ layerهای قدیمی با تاریخ نامعلوم به‌صراحت شناسایی شوند، بدون جعل تاریخ از `ReceivedAtUtc`. فروش فقط layerهای واجد تاریخ را انتخاب کند و ترتیب برابر بودن تاریخ‌ها قطعی باشد. index و query قفل با هم بازبینی شوند تا range-lock و جلوگیری از oversell حفظ شوند.
4. semantics فعلی `Posted` و endpoint ترکیبی خرید به‌صورت صریح محافظت شود؛ مسیر جدید و قدیم نتوانند برای همان مقدار دو بار موجودی یا ledger بسازند. هیچ ledger شریک یا هزینهٔ دیررس جدید بر اساس فرض مالی تولید نشود؛ قبل از استفادهٔ عملیاتی سازگاری کامل با posting فعلی مشخص و آزموده شود.

Migration فقط افزایشی باشد؛ data mapping، سازگاری API و rollback پیش از اجرا بررسی شوند. JSONهای فرم‌ها، `frontend/src/components/base-form/formIntegrationRegistry.ts` و مسیرهای عملیاتی تأییدشده در این بسته تغییر نکنند. UI خرید و handoff آزمایشگاه بستهٔ بعدی‌اند.

## آزمون‌های پذیرش متمرکز

روی SQL Server disposable با اتصال صریح و بدون fallback به DB اصلی، migration و fixture مصنوعی اجرا شود. قبل از راه‌اندازی app، هدف اتصال و `Database:AutoMigrate`/`Seed:Enabled` کنترل شوند. نیازی به restore دادهٔ واقعی برای این تست‌ها نیست.

- فاکتور روز ۱ بدون PO؛ رسید ۶ واحد روز ۱۰ و رسید ۴ واحد روز ۲۰؛ فروش روز ۱۵ فقط از رسید روز ۱۰ مصرف کند و موجودی به تفکیک تاریخ صحیح باشد.
- دو receipt جزئی، مقدار مغایر با invoice و ردیابی receipt→layer→movement؛ ثبت مضاعف و retry همزمان، یک اثر داشته باشند.
- دو فروش همزمان برای موجودی محدود، عدم oversell، rollback اتمیک و حفظ reversal/lineage؛ ترتیب قطعی برای رسیدهای هم‌روز.
- مسیر فعلی purchase posting و مسیر جدید برای یک invoice اثر دوگانه نسازند؛ قرارداد effective-date و مجوزها در برابر regression بررسی شوند.
- migration روی DB خالی و نمونهٔ سازگار با schema فعلی؛ layer قدیمی بدون تاریخ معتبر پنهانی eligible نشود. query plan و قفل index روی SQL واقعی بررسی شوند.

این‌ها معیارهای آینده‌اند، نه آزمون‌های انجام‌شده. در ممیزی قبل `YARN_TRADE_SQL_TEST_CONNECTION` موجود نبود و تست SQL اجرا نشد؛ جزئیات در [نتایج آزمون](operational-test-results.md).

## تصمیم‌های واقعاً مانع این بسته

1. **اختلاف مقدار:** دریافت بیش از مقدار فاکتور مجاز است یا باید متوقف شود؟ دریافت کمتر می‌تواند به‌صورت جزئی ثبت شود؛ تعیین اثر مالی کسری برای بستهٔ هزینه موکول است.
2. **ترتیب یک‌روز:** اگر چند رسید یک کالا در یک روز باشند و زمان واقعی موجود نباشد، ترتیب ثبت/شمارهٔ رسید مبنای FIFO باشد؟ این انتخاب باید قابل ردیابی و ثابت باشد.
3. **اسناد قطعی موجود:** رفتار مجاز برای خریدهای قبلاً `Posted` و رسیدی که تاریخش پیش از فروش قطعی موجود است چیست؟ پیشنهاد محافظه‌کارانه: از ثبت اثر دوگانه یا تغییر تخصیص فروش قبلی جلوگیری و مورد برای بررسی دستی متوقف شود. گزارش SQL قبلی layer/movement صفر داشت، ولی پیش از migration باید وضعیت دوباره بررسی شود.

تاریخ واقعی receipt و مقدار واقعی طبق درخواست مالک قطعی‌اند. قواعد FX، سهم سود، claim، bounce و تخصیص هزینهٔ دیررس برای پیاده‌سازی receipt و محافظت FIFO لازم نیستند؛ نباید در این بسته حدس زده شوند. دسترسی به SQL ایزوله مانع **اجرای پذیرش** است، نه تصمیم تجاری مالک.
